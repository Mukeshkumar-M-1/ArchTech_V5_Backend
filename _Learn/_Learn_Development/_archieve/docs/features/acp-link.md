# acp-link — ACP Proxy Server

> Source Directory: `packages/acp-link/`
> PR: #292
> Date Added: 2026-04-18

## I. Feature Overview

`acp-link` is an ACP (Agent Client Protocol) proxy server that bridges WebSocket clients to the stdio interface of an ACP agent. It allows ACP agents (such as Claude Code) to be accessed remotely via WebSocket, rather than being restricted to local stdio.

### Core Features

- **WebSocket → stdio Bridging**: Converts WebSocket connections from browsers/remote clients into NDJSON streams for the ACP agent's stdin/stdout.
- **Session Management**: Create, load, resume, list, and close sessions.
- **Permission Approval Flow**: Allows clients to remotely approve tool permission requests from the agent.
- **RCS Integration**: Can connect with the Remote Control Server (RCS) to register the ACP agent and interact via the Web UI.
- **HTTPS Support**: Built-in self-signed certificate generation for secure connections.
- **Token Authentication**: Automatically generates a token or allows configuration via environment variables.

## III. Installation and Usage

### Basic Usage

```bash
# Run directly (within the monorepo)
# Note: Claude itself does not support ACP; you need to start an ACP agent with ccb-bun --acp
bun packages/acp-link/src/cli/bin.ts ccb-bun -- --acp

# Specify port and host
acp-link --port 9000 --host 0.0.0.0 ccb-bun -- --acp

# Enable HTTPS (self-signed certificate)
acp-link --https ccb-bun -- --acp

# Debug mode
acp-link --debug ccb-bun -- --acp
```

### CLI Reference

```
USAGE
  acp-link [--port value] [--host value] [--debug] [--no-auth] [--https] <command>...
  acp-link --help
  acp-link --version

FLAGS
       [--port]     Port to listen on                  [default = 9315]
       [--host]     Host to bind to                    [default = localhost]
       [--debug]    Enable debug logging to file
       [--no-auth]  Disable authentication (dangerous)
       [--https]    Enable HTTPS with self-signed cert
    -h  --help      Print help information and exit
    -v  --version   Print version information and exit

ARGUMENTS
  command...  Agent command followed by its arguments (e.g. "ccb-bun -- --acp")
```

## IV. Authentication

A random token is generated by default at startup. Clients should not include the token in the URL when connecting:

```
ws://localhost:9315/ws
```

WebSocket clients that cannot send an `Authorization` header must use the `rcs.auth.<base64url-token>` subprotocol to pass the token.

Configure a fixed token:

```bash
ACP_AUTH_TOKEN=my-fixed-token acp-link ccb-bun -- --acp
```

Disable authentication (not recommended, development only):

```bash
acp-link --no-auth ccb-bun -- --acp
```

## V. RCS Integration

`acp-link` supports registering an ACP agent with the Remote Control Server for remote control via a Web UI.

### Connection Method

```bash
# Configure RCS connection via environment variables
ACP_RCS_URL=http://localhost:3000 \
ACP_RCS_TOKEN=sk-rcs-your-key \
acp-link ccb-bun -- --acp
```

### Registration Process (Two Steps)

1.  **REST Registration**: Register the environment with RCS via `POST /v1/environments/bridge`.
2.  **WS Identify**: After establishing a WebSocket connection, send an `identify` message (containing `agentId`) instead of a full `register`.

ACP WebSocket connections for RCS do not accept tokens in the URL query. `acp-link` sends the `ACP_RCS_TOKEN` via the `rcs.auth.<base64url-token>` WebSocket subprotocol.

```
acp-link                          RCS
   │                                │
   │── POST /v1/environments/bridge ──►│  (REST Registration)
   │◄── { agentId, sessionId } ───────│
   │                                │
   │── WS connect ─────────────────►│  (WebSocket)
   │── identify { agentId } ────────►│  (WS Identification)
   │◄── identified ─────────────────│
   │                                │
   │── ACP events ─────────────────►│  (Bidirectional message forwarding)
   │◄── user prompts/permissions ───│
```

## VI. Permission Modes

### permissionMode Transmission Chain

The permission mode is passed through the entire chain: Web UI → RCS → acp-link → ACP agent.

Supported permission modes:
- `default` — Prompt for permission for each request
- `auto` — Automatic judgment
- `acceptEdits` — Automatically accept edits
- `plan` — Planning mode
- `dontAsk` — Do not ask
- `bypassPermissions` — Bypass permissions (requires sandbox environment)

### Fallback Chain

When the client does not explicitly pass a `permissionMode`, the following fallback chain is used:

```
Client value > config.permissionMode > ACP_PERMISSION_MODE environment variable
```

Example:

```bash
ACP_PERMISSION_MODE=auto acp-link ccb-bun -- --acp
```

## VII. Permission Pipeline (2026-04-18 Improvements)

### Mode Synchronization

`applySessionMode` synchronizes `appState.toolPermissionContext.mode` when the agent switches permission modes, ensuring consistency between the internal permission context and the ACP client state.

### Unified Permission Pipeline

`createAcpCanUseTool` integrates into the `hasPermissionsToUseTool` unified permission pipeline, replacing scattered processing logic. It supports the `onModeChange` callback for real-time synchronization when the mode changes.

### Bypass Detection

An availability check is added for the `bypassPermissions` mode—it is only allowed in non-root or sandbox environments to prevent security risks associated with bypassing permissions.
