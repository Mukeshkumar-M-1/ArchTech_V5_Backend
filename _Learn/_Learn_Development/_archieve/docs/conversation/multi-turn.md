## Single-turn vs Multi-turn: Architectural Differences

- **Single-turn** (One Agentic Loop): A single complete execution of the `query()` function—assembling context → calling the API → handling tool calls → looping until completion.
- **Multi-turn** (One Session): A single conversation managed by the `QueryEngine` class—spanning dozens of `submitMessage()` calls and lasting for hours.

`QueryEngine` (`src/QueryEngine.ts`, class definition) is the **session orchestrator** sitting above the single-turn Agentic Loop. It manages state far beyond just a list of messages:

```
Internal State of QueryEngine (src/QueryEngine.ts constructor)
├── mutableMessages: Message[]         ← Full conversation history, accumulated across turns
├── readFileState: FileStateCache      ← Cached contents of read files to avoid duplicate reads
├── totalUsage: NonNullableUsage       ← Cumulative token consumption (input/output/cache)
├── permissionDenials: SDKPermissionDenial[]  ← Record of permission denials
├── discoveredSkillNames: Set<string>  ← Skills discovered in the current turn
├── loadedNestedMemoryPaths: Set<string>  ← Loaded nested memory paths (to prevent duplicates)
├── hasHandledOrphanedPermission: boolean  ← Whether orphaned permission requests have been handled
└── abortController: AbortController   ← Session-level interruption control
```

## QueryEngine's Core Method: submitMessage()

Every time a user inputs a message, the REPL or SDK calls `submitMessage()`, which executes the full turn initialization pipeline:

```typescript
// src/QueryEngine.ts — Simplified flow of QueryEngine.submitMessage()
async *submitMessage(
  prompt: string | ContentBlockParam[],
  options?: { uuid?: string; isMeta?: boolean },
): AsyncGenerator<SDKMessage> {
  // 1. Clear turn-level tracking state
  this.discoveredSkillNames.clear()

  // 2. Resolve the model (the user might have switched models via setModel() midway)
  const mainLoopModel = this.config.userSpecifiedModel
    ? parseUserSpecifiedModel(this.config.userSpecifiedModel)
    : getMainLoopModel()

  // 3. Dynamically assemble the System Prompt (reconstructed for each turn)
  const { defaultSystemPrompt, userContext, systemContext } =
    await fetchSystemPromptParts({ tools, mainLoopModel, mcpClients })

  // 4. Wrap permission checks (tracking each denial)
  const wrappedCanUseTool = async (tool, input, ...) => {
    const result = await canUseTool(tool, input, ...)
    if (result.behavior !== 'allow') {
      this.permissionDenials.push({
        type: 'permission_denial',
        tool_name: sdkCompatToolName(tool.name),
        tool_call_id: toolUseID,
        tool_input: input,
      })
    }
    return result
  }

  // 5. Call the core query() function to execute the agentic loop
  yield* query({
    systemPrompt, messages: this.mutableMessages,
    tools, model: mainLoopModel, ...
  })
}
```

Key design choice: `submitMessage()` is an `async *Generator`—it yields `SDKMessage` step-by-step, allowing the caller (REPL/SDK) to display progress in real-time rather than waiting for the entire turn to finish.

## Session Persistence: JSONL Transcript

Every conversation event is appended to a transcript file (`src/utils/sessionStorage.ts`):

### Storage Path

```
~/.claude/projects/<sanitized-cwd>/<session-uuid>.jsonl
```

- The path is generated by `getProjectDir(originalCwd)`, using `sanitizePath()` to convert the project directory path into a safe directory name (not a hash). Sessions for the same project directory are grouped into the same subdirectory.
- Each record is a single line of JSON (JSONL format), supporting append-only writes without needing to read-modify-write the entire file.
- The read limit is set to 50MB (`MAX_TRANSCRIPT_READ_BYTES` constant in `src/utils/sessionStorage.ts`) to prevent OOM errors for oversized sessions.

### Transcript Writer

The `Project` class (`src/utils/sessionStorage.ts`, private class) manages transcript writes. It uses `writeQueues` (write queues grouped by file) and `drainWriteQueue()` (scheduled batch flushing) to ensure that concurrent message appends do not overwrite each other:

```
Write Flow (Asynchronous Queued Path):
  recordTranscript(sessionId, entry)
    ↓
  project.enqueueWrite(filePath, entry)    ← Enqueue to writeQueues
    ↓
  scheduleDrain()                          ← Set timer (FLUSH_INTERVAL_MS)
    ↓
  drainWriteQueue()                        ← Batch by MAX_CHUNK_BYTES
    ↓  Write each batch
  appendToFile(path, batchContent)         ← Bulk append
    ↓
  If remote persistence is configured:
    persistToRemote(sessionId, entry)
      ├── CCR v2: internalEventWriter('transcript', entry)
      └── v1 Ingress: sessionIngress.appendSessionLog(...)

Synchronous Direct Write Path (used for metadata rewriting, etc.):
  appendEntryToFile(fullPath, entry)       ← Synchronous appendFileSync
    ↓
  mkdir + retry on failure
```

### Session Resume Pipeline

The resume flow triggered by the `--resume` parameter (`--resume` branch in `src/main.tsx`):

```
1. Parse resume parameter:
   ├── UUID format → getTranscriptPathForSession(uuid)
   ├── .jsonl file path → Use directly
   └── boolean → Picker for the most recent session

2. loadTranscriptFromFile(path)
   ├── Parse as JSONL lines
   ├── Filter for message-type records
   └── Rebuild the Message[] array

3. Restore context state:
   ├── restoreCostStateForSession(sessionId)  ← Restore cumulative costs
   ├── Restore agentSetting (user-selected Agent type)
   └── If --rewind-files is present, restore files to the snapshot at the specified message

4. Create QueryEngine({ initialMessages: restoredMessages })
   └── Continue the conversation from the restored messages
```

## Cost Tracking: From API Usage to USD

Cost tracking spans three modules, forming a complete record → accumulate → display pipeline:

### Record Layer: Usage in API Responses

Each `message_delta` event carries a `usage` field (`input_tokens`, `output_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens`). `accumulateUsage()` adds incremental usage to the session total.

### Accumulation Layer: cost-tracker.ts

```typescript
// src/cost-tracker.ts — StoredCostState type definition
type StoredCostState = {
  totalCostUSD: number; // Cumulative cost in USD
  totalAPIDuration: number; // Total API call duration (including retries)
  totalAPIDurationWithoutRetries: number; // Pure inference time without retries
  totalToolDuration: number; // Total tool execution duration
  totalLinesAdded: number; // Number of code lines added
  totalLinesRemoved: number; // Number of code lines removed
  lastDuration: number | undefined; // Duration of the last session
  modelUsage: { [modelName: string]: ModelUsage } | undefined; // Usage broken down by model
};
```

`addToTotalSessionCost()` calculates the cost of each API call based on model pricing and adds it to `totalCostUSD`. `ModelUsage` per model supports separate statistics when switching models within the same session.

### Persistence: Retained Across Restarts

```typescript
// Save to project config at the end of each session
saveCurrentSessionCosts(sessionId)
  → projectConfig.lastCost = totalCostUSD
  → projectConfig.lastSessionId = sessionId
  → projectConfig.lastModelUsage = modelUsage
```

### Budget Circuit Breaker

`QueryEngineConfig.maxBudgetUsd` provides a hard session-level budget limit. In the REPL, when cumulative costs exceed $5 (fee threshold `useEffect` in `src/screens/REPL.tsx`), a cost alert dialog pops up—this is not a hard block but a "soft reminder", and it only shows if `hasConsoleBillingAccess()` is true.

## Hot-swapping Models

Switching models within a session does not lose conversation history—because `mutableMessages` is decoupled from the model selection:

```
/model sonnet → QueryEngine.setModel('claude-sonnet-4-20250514')
  ↓  Actual operation: this.config.userSpecifiedModel = model (QueryEngine.setModel() method)
At the start of the next submitMessage():
  ↓
parseUserSpecifiedModel(this.config.userSpecifiedModel)
  → Returns the new model configuration
  ↓
fetchSystemPromptParts({ mainLoopModel: newModel })
  → System Prompt is reassembled based on the new model's capabilities
  ↓
query({ model: newModel, messages: this.mutableMessages })
  → Continue the conversation using the full history + the new model
```

When switching models, `contextWindowTokens` and `maxOutputTokens` are also recalculated based on the new model's specifications—for example, when switching from Sonnet to Opus, the context window might increase from 200K to 1M.

## File Snapshots and Rollbacks

`fileHistoryMakeSnapshot()` (`src/utils/fileHistory.ts`) automatically saves current content before the AI modifies a file. Snapshots are bound to a specific `message.id`, allowing `--rewind-files <user-message-id>` to accurately restore the file state to any point in the conversation—this is more fine-grained than git (which only tracks committed content).
